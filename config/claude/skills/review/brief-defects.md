# Review brief: Defects

Before starting, read the Lenses below and `lenses-shared.md` in this folder, then the Defects lenses and Pinned additions of each domain file your prompt names. Deliver per "Review hits" in `~/.claude/skills/review/return-rule.md`.

## Steps

1. List every changed file and every changed function, instruction, handler, or endpoint. Every item gets a line in your return, in the "Coverage line format" of `return-rule.md`: the hits under it, or "checked, nothing", plus the fields its class requires (`sig:`, `arms:`/`examples:`, `probe:`, `order:`, `parity:`, and always `lenses:`). Fill each field from the code before you decide the item is clear: the field is the check, not its record. A `sig:` that is not `unchanged` is a Contract hit unless you name the changeset tier that admits it. A `probe:` that admits a type the code does not mean is a Falsy branch hit. An `order:` with an override, an RPC call, or a fallback ahead of a capability or signer check is a Reorder hit. An item is one function, handler, or endpoint; a line that names several has checked none of them. "Rename only", "moved", "unchanged from base", "same as develop", "pre-existing", "the spec or README says so", and "the changeset or a comment documents it" are not reasons: a moved or extracted item is the diff's and gets the full check, and a document is a claim the Contract lens tests. Triage greps these lines and sends every line without its fields, or with one of those reasons, back as a hit.
2. When the prompt names a `prior.md`, add each follow-up in it as an item:
   - a prior comment the author replied to: read the reply and the code
   - a claim the author left unverified: read the code, and run the narrowest test that settles it

   Report a hit where the code does not back the reply or the claim. A claim closes by a run, never by a reading: when no test reaches it, list it as a revert-check target with the mutant that would prove it.

3. For each lens, walk the diff and report every hit as `file:line`, the lens name, the concrete failure scenario (the input or state, then the wrong output or behaviour), and the minimal fix. Older code is the diff's when the diff calls it, moves or extracts it, widens who reaches it, or makes an outcome depend on it: its defect is a hit. Show every derivation for a number you re-derive.
4. Prove each hit by a run where one is possible: the narrowest test, a script, or a repro that shows the wrong outcome. Save its output under the scratchpad path the prompt names, and put the command and output path in the hit. Where nothing can run it, say so and quote the `file:line` that settles it. Triage confirms from that or dismisses it; no verifier reads it after you.
5. Rank hits high, medium, low by user-visible consequence. Hits have no length cap; the suspicions list stays under 200 words.

## Lenses

Each lens is a class of defect to look for, then how to check it. A lens names a class, never last round's instance; a fixed syntactic pattern belongs in a lint rule or CI check.

- **Re-derive** — a literal the diff introduces or relies on: byte size, window length, offset, threshold, timeout, version floor. → Compute it from the source it claims to come from (`size_of`, `INIT_SPACE`, a program or contract constant, an on-chain account) and compare. Comments, commit messages, and PR bodies are claims, not evidence.
- **Mirror** — off-chain code that reproduces an on-chain or remote rule: a client computing what a program will require, a TS condition copying a Rust or Solidity check. → Put the two conditions side by side, operator by operator (`<` against `<=`, which flags gate which branch). Flag every pair that can disagree, including a pre-existing asymmetry the diff now makes load-bearing.
- **Safe side** — a default parameter, a fallback, or a changed direction of error. → Name which side is the safe failure (over-quote beats under-quote; a throw beats a silent fallback to a mainnet constant) and confirm the new behaviour lands there. A callee with no in-repo consumers hands every external caller the new default silently.
- **Failure mode** — a removed panic, `unwrap`, throw, revert, or overflow, and every new catch that logs and continues. → State what the path does now instead (retry, permanent stop, silent convergence) and whether that is the intended response. One hardened operation beside unchecked neighbours (`saturating_sub` next to an unchecked `* 2`) is half a fix. A zero-valued guard (`0 >= 0`) passes when it should fail. A path that leaves a stale value (warn and continue, a fallback to the old stamp) names what repairs that value later: the next run, a retry, a reconcile job. Trace that repair through the real code, and through a crash between two writes. When nothing repairs the value, the stale state is permanent, and the severity follows from that. A spec that accepts the failure path accepts it only as far as the spec traced it. Every hold, skip, fallback, or exhausted retry reaches an operator: a log at `warn` or above, or a metric an alert reads. A log on the same path that says the opposite is a hit.
- **Fix chain** — a fix for a hazard that an earlier fix on the branch created (a second transaction, then a deadlock, then a retry loop). → Name the design choice both hazards come from and the smallest design that removes both (the write moves into the transaction that already exists). The hit is against the choice, not the latest patch.
- **Breadth** — a loop, retry, or window that now covers less than before: an exit (`break`, `continue`, `return`, `?`) in a loop that validates, aggregates, or settles a list, a loop of candidates replaced by one attempt, a retry that drops its parameters, a lookback window shorter than the gap between runs. → Name what the skipped iterations or attempts were supposed to check, and confirm every item is still accounted for.
- **Cost** — a new or widened request path. → Bound the work per request (derivations, RPC calls, entries) in terms of the inputs a caller controls. A rate limiter bounds the rate, not the cost of one call. State the bound or the lack of one.
- **Pinned** — every test added or changed. →
  - (a) _Revert check_: mentally revert the fix the test is named for and confirm the test goes red; a test green either way pins nothing. The fix includes its data flow, not only its guards: a call site's return value or argument replaced by `[]`, `null`, or `0` is a revert too. Triage runs this check for real on every target in "Revert check" in `review-rules.md` that a unit test file reaches (guards, call sites, added predicate terms, changed signatures, cited tests), so spend the lens on the ones no unit test file reaches.
  - (b) The expectation comes from outside the code under test: a literal, or the artifact read back from the chain or the database, never the same helper the handler calls.
  - (c) Every guard the diff adds (a `require!`, a `revert`, a new error variant, a new early return) has a test that reaches it.
  - (d) An implicit precondition (time of day, epoch boundary, a cron that has not fired yet) is stated in the test or removed by pinning the clock. A unit test that waits in real time for a poller, a timer, or a timeout is a low hit, with fake timers in the test as its fix: every revert-check target pays that wait again.
  - (e) _Negative test_: every new signer, owner, role, mint, seeds, or amount constraint has a test that reaches it with the wrong signer, owner, role, mint, seeds, or amount and asserts the specific error, not just "it threw".
  - (f) _CI runs it_: name the CI job that runs each new or changed test file. A test no job runs pins nothing, in every domain: it is a hit with the workflow change as its fix, never a coverage note. Check workspace `exclude` lists and each workflow's test command.
  - (g) _Reachable fixture_: every fixture or mock input is a state the real system can reach. Derive it from the setup path the code runs (rent plus reserve, never below the rent floor), not a literal.
  - (h) The Pinned additions of each domain file.
- **CI truth** — every red check on the head, and every change made to fix a failing job. → A red check is the diff's until the base's latest run of the same job is red too: look it up (`gh run list --branch <base> --workflow <file>`). The diff's tool, image, and dependency version bumps are the first suspect. Give each failing job its own failure signature; one shared cause for many jobs is a claim to check per job. The PR body's attribution is a claim, not evidence. For a fix, reproduce the failure and confirm this change removes it. "The job passed on rerun" and "the change fixed it" are different facts. For an image or build change, run the produced artifact, not only the build.
- **Identity** — any input that names a wallet, user, or principal. → Confirm it is authenticated upstream and that no new path trusts it unverified.
